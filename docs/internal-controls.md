# Internal Controls

This document lists the internal controls implemented in the application. Each
row names the business risk the control addresses, how the control is actually
implemented, and where it can be seen in the code. Every control named in section
11 of the specification is implemented; the closing section states the honest
limitations of a fully client-side system.

## Control matrix

| Control | Business risk it mitigates | How it is implemented in this system | Where to see it |
|---|---|---|---|
| **User authentication** | An unauthorised person opens the books and acts as a real user; passwords leaking from storage. | A login verifies the typed password against `User.passwordHash`, which is `SHA-256(salt + ':' + password)` with a per-user 16-byte random salt (`makeSalt`, `hashPassword`, `verifyPassword`). Comparison is timing-resistant (`timingSafeEqual`), and `validatePasswordStrength` enforces a minimum length plus at least one letter and one digit. The `users` table has the unique index `&username`. **Session timeout**: any interaction resets an idle clock and after `SESSION_TIMEOUT_MINUTES` (30) of inactivity the shell signs the user out, records a `LOGOUT` audit row and returns to the login screen. | `src/services/auth.ts` (`hashPassword`, `verifyPassword`, `timingSafeEqual`, `validatePasswordStrength`, `SESSION_TIMEOUT_MS`); `users` table in `src/db/schema.ts`; idle enforcement and sign-out in `src/components/Layout.tsx`; `logout` in `src/services/admin.ts`. |
| **Role-based access** | Staff performing actions outside their responsibility or seniority. | One permission matrix (`MATRIX`) maps each of the six roles — `ADMIN`, `ACCOUNTANT`, `PURCHASE_OFFICER`, `SALES_OFFICER`, `APPROVER`, `AUDITOR` — to a list of permissions. Menu and action checks call `can(role, permission)`; `permissionsFor` and `canAny` support the navigation build. | `src/services/auth.ts` (`ROLES`, `ROLE_DESCRIPTIONS`, `MATRIX`, `can`, `permissionsFor`, `canAny`). |
| **Approval hierarchy** | Junior staff authorising large or unusual payments. | `APPROVAL_THRESHOLD` is `2_500_000` paise (₹25,000). `canApproveAmount(role, amount)` returns unlimited authority for `ADMIN` and up to the threshold for `APPROVER`; `approverRolesFor` lists who may approve a given amount and `approvalLimitDescription` explains the limit to the user. Approval is refused above the limit by `approveVoucher`. | `src/services/controls.ts` (`APPROVAL_THRESHOLD`, `canApproveAmount`, `approverRolesFor`, `approvalLimitDescription`); enforced in `src/services/ledger.ts` (`approveVoucher`). |
| **Voucher authorization (maker–checker)** | One person creating and approving their own voucher, so no independent check exists. | `assertMakerChecker(preparedBy, approverUserId)` throws if the approver is the same user who prepared the voucher. It is called at the start of the approval step, so a voucher can only move from `PENDING` to `APPROVED` by a different user. | `src/services/controls.ts` (`assertMakerChecker`); called in `src/services/ledger.ts` (`approveVoucher`). |
| **Payment request & release** | A payment leaving the bank without an independent approval, or settling the wrong invoices. | A payment may be raised as a *request*: it is parked as a `PENDING` voucher and its intended invoice settlement is stored under `settlement.plan.<id>` in `settings`; no ledger entry is written and no invoice is settled. `releaseSettlement` approves it (running the same maker–checker and threshold checks), posts it, and applies the plan — all in one transaction, so the ledger entry and the allocations commit together. `postVoucher` also applies a stored plan, so a request posted from any other screen still settles correctly. | `src/services/cashbank.ts` (`createPayment`, `releaseSettlement`, `settlementPlanFor`); `src/services/allocations.ts`; `src/services/ledger.ts` (`postVoucher`). |
| **Audit trail** | Changes happening with no record of who did what, when. | `writeAudit` appends an `AuditLogEntry` (`ts`, `userId`, `username`, `action`, `entity`, `entityId`, `summary`, `before`, `after`) for every `CREATE`, `SUBMIT`, `APPROVE`, `POST` and `REVERSE`, and the audit module lists `LOGIN`, `BACKUP` and `RESET` as its other intended actions. The log is append-only — there is no update or delete path anywhere in the application. `queryAuditLog` filters by date, user, action, entity and free-text search. | `src/services/audit.ts` (`writeAudit`, `queryAuditLog`, `countAuditEntries`); `auditLog` table in `src/db/schema.ts`. |
| **Voucher immutability** | Editing a posted entry to conceal a mistake or fraud. | A posted voucher's ledger rows are never updated. `postVoucher` refuses a voucher that already has entries, and the only permitted correction is `reverseVoucher`, which posts a mirror voucher built by `reverseLines`, marks the original `REVERSED` and records the reversal id in `reversedBy`. `postVoucher` also refuses to post a `DRAFT`, `PENDING` or already `REVERSED` voucher. | `src/services/ledger.ts` (`postVoucher`, `reverseVoucher`); `src/engine/validators.ts` (`reverseLines`). |
| **Audit written in the same transaction** | A business change committing without its audit entry, or the log going missing. | `writeTx` wraps every multi-step action in a single Dexie read-write transaction across all tables, and `writeAudit` is called inside that same transaction, so a failed audit rolls the whole business change back. | `src/db/tx.ts` (`writeTx`, `ALL_TABLES`); `src/services/audit.ts` (`writeAudit`). |
| **Segregation of duties** | The same person raising a purchase and releasing the payment, or keeping the books and approving them. | The permission matrix keeps duties apart: `PURCHASE_OFFICER` holds only `purchase.create` and `reports.view` (never `payment.create`), `SALES_OFFICER` holds only `sales.create` and `reports.view` (never `receipt.create`), `ACCOUNTANT` can create and post vouchers but never approves (`voucher.approve` is absent), and `AUDITOR` holds only `reports.view` and `audit.view`. | `src/services/auth.ts` (`MATRIX`), cross-checked against `ROLE_DESCRIPTIONS`. |
| **Duplicate prevention** | Paying the same supplier invoice twice; issuing two documents with the same number. | The `invoices` table carries the unique compound index `&[type+partyId+partyInvoiceNumber]`, so the same supplier invoice number cannot be recorded twice for the same supplier; `duplicateInvoiceMessage` produces the operator-facing explanation. For receipts, `looksLikeDuplicateReceipt` raises a soft warning when the same party, amount and date repeat, because a genuine second payment is possible. Voucher numbers come from `allocateSequence`, which increments the `sequences` row atomically and cannot issue a duplicate, and the `vouchers` table adds the unique index `&[type+number]` as a second line of defence. | `src/db/schema.ts` (`invoices` and `vouchers` store strings); `src/services/controls.ts` (`duplicateInvoiceMessage`, `looksLikeDuplicateReceipt`); `src/engine/numbering.ts` (`allocateSequence`). |
| **Gapless numbering** | Gaps in a voucher series that hide a deleted document. | `allocateSequence` reads the next value from the `sequences` table and writes it back in one transaction; cancelled documents are deleted rather than skipped, and allocations never roll back, so the series has no gaps. `peekSequence` shows the operator the number that will be used before saving. | `src/engine/numbering.ts` (`allocateSequence`, `peekSequence`, `formatDocNumber`). |
| **Period lock** | Back-dated entries silently changing a closed month or year. | The `periodLocks` table stores a lock for either a month (`type = 'MONTH'`) or a financial year (`type = 'FY'`), with the unique index `&[period+type]`. `isDateLocked` and `lockCoveringDate` test a date against the locks, and `assertPeriodOpen` throws before any posting into a locked period. | `src/services/controls.ts` (`isDateLocked`, `lockCoveringDate`, `describePeriodLock`); `src/services/ledger.ts` (`assertPeriodOpen`, called by `createVoucher`, `postVoucher` and `reverseVoucher`); `periodLocks` table in `src/db/schema.ts`. |
| **Balanced postings (the golden rule)** | An unbalanced voucher corrupting the trial balance and financial statements. | `assertBalanced` requires total debits to equal total credits and rejects negative amounts, lines that are both a debit and a credit, zero-amount lines and empty vouchers. It is called by every transaction poster and again by `createVoucher`. Genuine rupee rounding is handled by `balanceWithRoundOff`, which posts the paise difference to the Round-off account (`5014`) so the voucher still balances. | `src/engine/validators.ts` (`assertBalanced`, `validateLines`, `balanceWithRoundOff`); `src/engine/posting.ts`; `src/services/ledger.ts` (`createVoucher`). |
| **Single write path to the ledger** | A stray code path inserting an unbalanced or untested journal. | `createVoucher` is documented and used as the only function that writes to `ledgerEntries`. It validates the lines, allocates a number, writes the voucher, writes the entries atomically when the voucher is posted, and writes the audit row. Lines for a not-yet-posted voucher are stashed under the key `voucher.lines.<id>` in `settings` and written by `postVoucher` after approval. | `src/services/ledger.ts` (`createVoucher`, `postVoucher`). |
| **Derived balances, never stored** | A cached balance drifting away from the underlying ledger. | No balance is stored anywhere. Reports recompute from `ledgerEntries` using `buildBalanceMap`, `netForAccount`, `mapTotals` and `rollupNet`; inventory quantity and value are recomputed from `stockMovements` by `replayMovements` and `valueIssue`. Because both sides are always derived, the ledger and the reports cannot disagree. | `src/reports/core.ts`; `src/services/inventory.ts`. |
| **Unique document keys** | Duplicate master records and duplicate runs. | Beyond the invoice index, the schema declares `users &username`, `payrollRuns &month` (a month can be run only once), `periodLocks &[period+type]`, `vouchers &[type+number]` and the composite index `attendance [employeeId+month]`. These are enforced by IndexedDB at write time. | `src/db/schema.ts` (`this.version(1).stores({ ... })`). |
| **Data backup** | Browser data loss wiping the books. | `exportBackup` serialises every table into a versioned JSON file (`format: 'sai-erp-backup'`) and stamps the time of the backup in `settings`; `importBackup` validates the format and version, clears and reloads every table in one transaction, and records a `RESTORE` audit row. `backupReminderDays` compares the last backup against `BACKUP_REMINDER_DAYS` (7) and the app shell shows a reminder banner when it is overdue. `resetAllData` rebuilds the seeded dataset through the seeder. | `src/services/backup.ts` (`exportBackup`, `importBackup`, `resetAllData`, `lastBackupAt`, `daysSinceLastBackup`, `backupReminderDays`); admin screen `src/pages/admin/BackupPage.tsx`; reminder in `src/components/Layout.tsx`. |

## Limitations of this implementation

These are stated deliberately, because a control that is only enforced in the
browser protects the user from mistakes rather than from a determined attacker.

1. **Data is per-browser.** The books live in IndexedDB through Dexie, in a
   single database named `sai-erp` (`src/db/schema.ts`). Clearing the browser's
   site data wipes everything, and there is no server, so two people on two
   machines do not share a set of books. There is no automatic off-device backup:
   the JSON export/import control above is the mitigation, and the shell reminds
   an administrator when it is overdue.

2. **Passwords use SHA-256, not a real password KDF.** `hashPassword` in
   `src/services/auth.ts` applies a single SHA-256 pass over `salt + ':' +
   password`. This keeps plaintext out of the database and uses a per-user random
   salt, but SHA-256 is fast and is not designed to resist offline brute-force
   attacks the way bcrypt, scrypt or Argon2 are. The code comment acknowledges
   this: a browser cannot provide those KDFs natively. For a production system
   the hash should be replaced with a proper KDF (or authentication moved to a
   server).

3. **Roles are enforced in the client.** The permission matrix in
   `src/services/auth.ts` (`can`, `permissionsFor`) and the controls in
   `src/services/controls.ts` all run in the single-page application. Because the
   app is fully client-side, a user with developer tools could bypass a check that
   is only enforced in the browser. The controls correctly demonstrate
   segregation of duties and maker–checker design, but they are not a substitute
   for server-side authorisation.

4. **The backup reminder is evaluated on load, not scheduled.** A static page has
   no background timer, so the "7 days without a backup" reminder is computed when
   an administrator opens a screen rather than fired by a scheduler. Every control
   in the matrix above is enforced by the code cited in its "Where to see it"
   column.
